# Field notes from real Gemma 4 E2B runs

Observations from running the prototype against Gemma 4 E2B through LiteRT-LM.js 0.14 on WebGPU in Chrome 151 (August 2026). Every claim below comes from a captured run in `sessions/generation-log.ndjson`; the byte-exact outputs that drove a fix are replayed in `src/captured-runs.test.ts`. Because LiteRT decodes greedily, a captured output is what the model emits again for that prompt, so a replay test and a live re-run agree.

## Runtime

- **LiteRT-LM.js 0.14 decodes greedily on WebGPU.** `samplerParams` with top-k > 1 is rejected ("Top-K value must be <= 1") and TOP_P sampling aborts the WASM with an out-of-range token. Temperature therefore has nothing to act on. An earlier iteration injected randomized "creative directions" to manufacture take-to-take variation; the prototype now embraces the determinism instead, and the same prompt reproducing the same surface is treated as a feature.
- **Model persistence matters more than model quality for iteration.** The 2.0 GB artifact is cached via the Cache Storage API (download → counting stream for byte progress → `cache.put` → `cache.match` → disk-backed `Blob` into `Engine.create`, sequentially so no tee backpressure can balloon memory). Measured: first load ≈ 3.5 minutes; every subsequent page load ≈ 2 seconds. Storage persistence is requested best-effort and quota is preflighted before caching.
- **Two things arrive over the network, once.** The model weights from Hugging Face, and LiteRT-LM.js's 19.8 MB WebGPU WASM runtime, which `@litert-lm/core` 0.14 fetches from jsDelivr (its `DEFAULT_WASM_PATH`, not overridable through the package's public exports). Prompts and generations never leave the browser.
- **Qwen 3 0.6B did not load** on LiteRT-LM.js 0.14: the runtime rejected its prefill/decode format. That was an empirical failure on one file and one version, not a documented policy; see `docs/fine-tuning-feasibility.md` for why it is worth re-testing on a newer release.

## How the model mis-serializes structure

- **Gemma emits flat depth-first sequences.** Containers frequently declare `children` inside `props`, as component *type names* rather than IDs, while the actual children simply follow in array order; final node objects sometimes lose closing braces, which `jsonrepair` splits into an envelope plus stray top-level nodes. The parser merges those fragments and the adoption pass reconstructs the intended tree. Without these recoveries, one run lost 21 of 29 nodes; with them the same output renders fully.
- **Gemma inlines children two different ways.** Instead of separate nodes it writes `"children":["TextField","label":"Full Name",…]` or `"children":["Button":{…}]`, invalid JSON that `jsonrepair` flattens into token streams. Salvage parses those streams back into real child nodes (a med-form run reconstructed 14 inline components across 5 containers and rendered first-try). A third variant never closes any node object at all: the whole stream parses as one object whose repeated `"id"` keys overwrite each other. Salvage detects the id-density mismatch and re-splits the text at each `"id"` boundary; one checkout run went from rendering a single heading to a complete 20+-element surface.
- **The model invented a parent-pointer syntax.** For the houseplant tracker it listed a Card's children as component type names, `"children":["Heading","Metric","ProgressBar","Tag"]`, and then emitted each of those leaves with *the Card's own id*. Duplicate-ID dedup kept the Card, the type names were pruned as missing references, and the empty-container sweep deleted the hollow Cards: 3 nodes rendered out of 21. Reading a leaf that reuses an earlier container's id as "this belongs to that container", the same emission-order principle as orphan adoption, brings the identical output to 21 nodes.
- **When whole-document repair fails, the `"id"` boundaries are still clean.** All three attempts of one houseplant run and the first checkout attempt died at `JSON.parse` even after `jsonrepair`: children inlined four levels deep, keys fused with their values (`"value:12"`, `"tone:warning"`), and a stray quote after each closed inline child (`{}}"}`). Splitting fused keys, re-splitting the text at each `"id":` and repairing every fragment alone, and retrying a failed fragment with the stray quote removed turned those into first-attempt renders: the formerly failed houseplant run yields 19 nodes in 16 s (it had burned three attempts and 55 s), and the checkout 28 nodes in 16 s (it had reached 8 nodes after three attempts and 52 s), including the four shipping fields the model had all named `shippingAddressField` and the place-order button.
- **The root's flat catch-all must not beat the model's real container.** Gemma habitually lists every component it is about to emit as children of the root, *and then* nests a subset properly. Settling that conflict by first-claim-wins handed the fields to the root, left the intake `Card` empty, and the empty-container sweep deleted it. Letting the root yield to any other claimant fixed it on byte-identical model output.

## What guardrails cannot do

- **The model drops items from long enumerations, and no prompt tweak fixed it.** A request naming six things ("customer name, phone, bike model, the problem, a drop-off date, and a request service button") produced four: name and phone were never emitted. Rewriting the form blueprint from "3-6 fields" to "one field per thing the request asks for" changed the output not at all, byte for byte, so the cause is the model's attention over a six-item list, not the field-count range. That change was reverted rather than shipped on an unproven rationale. Salvage reconstructs structure the model mis-serialized; it cannot recover content the model never generated.
- **A format migration can silently delete content, and only the raw log catches it.** Switching the model to native A2UI syntax made `value` the binding slot, and salvage stripped it from *every* component before prop coercion, so every `Metric` lost its value and was dropped as invalid: four in the project dashboard, three in sourdough, three in the investment comparison. The rendered surfaces still looked plausible, which is exactly why the per-run warning list and the NDJSON log exist. The fix reserves `value` only on the three bindable inputs. Byte-identical replays: dashboard 17 → 23 nodes with all four metrics, sourdough 16 → 20, comparison 12 → 15.
- **The guardrail count is a model-quality metric only if the categories are honest.** Counting a type-name annotation as a "pruned missing reference" or an empty reconstruction artifact as a "dropped Heading" inflates the number. The warning families name what actually happened (re-split, re-homed, renamed, ignored annotation, adopted, grouped), so a spike means the model looped or truncated, and the debug trace says which.

## Measured outcomes

- **First-pass viability is high with salvage on.** Measured live on 24 August 2026 after the native-syntax fixes: the houseplant tracker rendered 19 nodes, the project dashboard 23, the checkout review 28, and sourdough mission control 20, every one on the first attempt in 13–16 seconds, with four to six logged adjustments each and no model repair round. Those adjustments are reconstruction (re-split, re-home, adopt, group), not content loss.
- **Recover versus Strict on the identical rocket-launch prompt (24 August 2026):** Recover rendered 18 components in 12.7 s with seven logged adjustments; Strict failed all three attempts at `JSON.parse` in 37.7 s, and its first attempt was byte-identical to the Recover run's. With deterministic decoding that difference *is* the salvage layer's contribution, reproducibly.
- **Replaying every logged first attempt (65 runs) through both paths on 8 September 2026:** 12 parse as JSON, 5 pass the strict schema untouched, and all 65 render through the salvage layer and the official processor. The layer was built from these logs, so 65 of 65 is an in-sample upper bound; the live tally while the layer was being built is 56 of 64 first-attempt renders and 63 of 64 overall.
- **Pattern fidelity after the blueprint change:** the intake form produced seven labeled fields (date/tel inputs, a medications Select, two TextAreas) in one card with a submit action; the support chat produced alternating named ChatBubbles with a reply box and send button with one salvage adjustment; the project dashboard produced four metrics with values in a grid, two progress bars, a tag row, a blocker alert, and two actions, each on the first attempt.
- **Native A2UI component syntax is cheaper than the bespoke format it replaced:** 337 vs. 366 characters on the same surface (92%), while asking the model to emit the full `createSurface`/`updateComponents`/`updateDataModel` stream costs 147% and requires multi-message serialization a 2B model does not reliably survive.
